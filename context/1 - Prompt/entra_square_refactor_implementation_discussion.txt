======================================================================
NARRATIVE SYNTHESIS
======================================================================

1. Starting Point
-----------------
azapp-nodejs-mcp began this discussion as a deliberately simplified, single-
tenant Square operations MCP server: a shared `x-api-key` header protected
`/mcp`, and exactly one Square merchant connection was stored under a single
fixed Key Vault secret (`square-oauth-primary`). This was a valid simplification
of an earlier, more elaborate Entra+Square enterprise design captured in a prior
export (chatgpt_mcp_entra_square_architecture_discussion.txt), but it could not
satisfy two new requirements: registering as an enterprise plugin in ChatGPT
(which requires real OAuth with PKCE/S256-capable authorization-server metadata)
and supporting multiple franchise owners, each with their own personal Square
seller account.

2. The Core Architectural Decision
-----------------------------------
Rather than re-adopting the original transcript's full multi-tenant design
wholesale, the actual business shape was clarified first: one Entra identity per
franchise owner, and one personal Square seller account per owner containing
many locations. That collapses the original design's
`EnterprisePrincipal 1:N SquareConnection` model down to a much simpler
`EnterprisePrincipal 1:1 SquareConnection`, with the existing
`SquareContext.authorizedLocations` already correctly modeling the "many
locations under one merchant" part. This one clarification avoided building an
unnecessary relational connection/merchant-selection layer.

3. Reusing the MCP SDK's Own OAuth Primitives
----------------------------------------------
Before writing any broker code, the actual `@modelcontextprotocol/server`,
`@modelcontextprotocol/express`, and `@modelcontextprotocol/node` package type
definitions were read directly rather than assumed. This surfaced that the SDK
(v2) already ships a complete OAuth Resource Server toolkit: `requireBearerAuth`,
the `OAuthTokenVerifier` contract, automatic `req.auth` -> `ctx.http.authInfo`
propagation into every tool call, and `mcpAuthMetadataRouter` for RFC 8414/9728
discovery documents. This meant the refactor's authentication plumbing was
mostly wiring existing SDK capabilities correctly rather than inventing new
mechanisms - notably, no AsyncLocalStorage or custom session store was needed to
carry the caller's identity into tool handlers.

4. The Broker
-------------
A small in-process OAuth authorization server ("broker") was added to the same
App Service, fronting Entra ID because Entra's own OIDC discovery document does
not reliably advertise `code_challenge_methods_supported`, which ChatGPT's MCP
client requires. The broker performs a standard confidential-client code
exchange against Entra, verifies the resulting ID token, and then issues its own
RS256-signed MCP access token (the first asymmetric signer in this codebase -
existing signers are HMAC because nothing external ever verified them). Pending
authorization requests and issued codes are intentionally kept in-memory rather
than in a database, a pragmatic simplification appropriate for a single-instance
deployment, with the tradeoff explicitly documented (won't survive restarts or
horizontal scale-out; no refresh_token grant yet).

5. Principal Propagation and Per-Owner Square Storage
-------------------------------------------------------
The verified principal (`tenantId:objectId`) flows automatically through the
SDK's existing `ctx.http.authInfo.extra`, is unwrapped once in a small shared
`Principal.js` helper, and reaches every tool as a plain `principal` argument -
keeping all auth-plumbing knowledge confined to `McpTool`/`ToolRegistry` rather
than spread across ten business tools. `SquareContextResolver` moved from one
global Key Vault secret to one secret per principal
(`square-oauth-{tenantId}-{objectId}`), and the Square account-linking flow was
changed so the one-time "Connect Square" link is only ever minted from inside an
already-authenticated MCP tool call and is itself signed and bound to that
principal - closing the account-binding attack path called out in the original
architecture discussion, without requiring a second independent Entra session
for the browser-facing linking routes.

6. A Real Bug Caught During Testing
-------------------------------------
Local smoke-testing against a deliberately unreachable dummy Key Vault caught a
genuine production-risk bug: an async Express route handler in
`OAuthBrokerController` had no try/catch around a Key Vault call, and its
rejection crashed the entire Node process rather than just failing that one
request - a known pitfall with Express 4's lack of automatic async-rejection
handling. Every handler in that controller was audited and wrapped, and the fix
was re-verified by confirming the server now answers with clean 500 responses
instead of exiting when Key Vault is unreachable.

7. Deployment and Secret Provisioning
----------------------------------------
Moving from local development to a real Azure App Service surfaced a concrete
configuration checklist: two required Application Settings (`KeyVaultUri`,
`SquareOAuthRedirectUri`), a system-assigned Managed Identity with write (not
just read) access to Key Vault (since the app both reads static secrets and
writes the broker's generated signing key plus per-owner Square tokens), HTTPS
Only, Always On, and a single-instance constraint tied directly to the broker's
in-memory OAuth state. Two HMAC signing keys
(`Square-OAuthStateSigningKey`, `Square-TipPreviewSigningKey`) had to be
generated and pre-provisioned manually, which was carried out live against the
user's real vault (enewbold-keyvault-02) after installing the Az PowerShell
module and signing in via device-code authentication. `Mcp-BrokerSigningKey`,
by contrast, does not need pre-provisioning - the app generates and persists it
itself on first use.

8. Registering with ChatGPT
------------------------------
Registering the deployed server as an MCP connector in ChatGPT's developer
console introduced two items outside the codebase's control: the console's
OAuth client configuration (resolved by noting the broker has no Dynamic Client
Registration endpoint, so ChatGPT likely needs a manually-entered, unvalidated
Client ID and no Client Secret, since the broker is a public PKCE-only client),
and a domain-ownership "Domain Verification" challenge requiring a specific
plain-text token to be served at a fixed `.well-known` path. The latter was
implemented as a small hardcoded constant and a static Express route, smoke-
tested locally to confirm the exact token string is returned, with redeployment
and live re-verification left as the final step. The broker's current
unrestricted acceptance of any `redirect_uri` (an open-redirect gap under
CWE-601 / OAuth Security BCP RFC 9700) was surfaced explicitly and deliberately
deferred at the user's request, to be revisited once ChatGPT's actual callback
URL is known.

9. Where Things Stand
------------------------
The refactor is implemented, locally smoke-tested, and deployed. Outstanding
follow-ups, all previously flagged rather than silently skipped: add a
refresh_token grant to the broker's token endpoint; lock `redirect_uri`
validation down to ChatGPT's actual callback host once known; and confirm the
domain-verification route is live on the deployed App Service before completing
ChatGPT's registration flow.
